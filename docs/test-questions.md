# Questions from the Build role about tests

The Build role (the `coder` subagent, or Claude Code in `pocket-game-night/`) cannot edit tests.
If a test looks wrong or impossible, add it here and tell the owner.
The Test role answers here and updates the test if the owner agrees.

| 2026-09-28 | `tests/browser/claims.spec.ts` "TAM-037, TAM-033, TAM-086, TAM-105: an accepted claim …" | `result.getByText(`${n} ✓`)` is a substring match, so when the five numbers include, say, 3 and 23, "3 ✓" matches both and the test fails at random (depends on the draw). The app shows each number as "23 ✓" in its own element as the README asks. Could it use `{ exact: true }`? | Yes, the test was wrong (Test role, 2026-09-28). TAM-037 asks for a ✓ next to each read-out number, so the test must find that number's own mark, not any mark that contains it. Both the ✓ check (accepted claim) and the ✗ check (bogey test) in `claims.spec.ts` now use `{ exact: true }`. Stricter, not looser. Scenario unchanged. |

| 2026-09-28 | `tests/browser/lifecycle.spec.ts` PLT-013 and PLT-012 (raised by the Test role) | On iPhone (WebKit), PLT-013 saw no request to keep data and PLT-012 saw no "storage nearly full" warning. Was the app at fault, or the test's stand-in for `navigator.storage.persist` / `estimate`? | The test was wrong (Test role, 2026-09-28). The stand-ins were set on the `navigator.storage` object itself. WebKit does not keep extra properties on that object unless the page holds on to it, so by the time the app asked, the stand-in was gone and the real browser function ran instead (checked: stand-in gone after setup; kept when the object is held or when set on `StorageManager.prototype`). Both tests now set the stand-in on `StorageManager.prototype` before the page loads, and also check that the stand-in is still the one the app would call, so they cannot pass or fail by accident. Stricter, not looser. Both pass on Android and iPhone. The round 1 report's line "the app is not asking" on iPhone was wrong. Scenarios unchanged. |
